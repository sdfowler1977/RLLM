# Connection authorization

Open App settings → Network services → LLM connections → Connection authorization. This optional flow supports a server-registered public client using an authorization code, S256 proof and bearer access tokens. Existing API-key connections continue working without these settings. No provider-specific key slot, SDK, client secret or hosted broker is required.

Configure the complete authorization endpoint, token endpoint, public client identifier and requested scopes. An optional expected issuer requires that exact issuer in the authorization return. Register the redirect URI shown in the form with your authorization server. The app derives it from its installed application identity: `com.local.client.lab.oauth:/callback` for the current Lab package, or `com.local.client.oauth:/callback` for the main package. Your authorization server must permit this native-app public client and support S256 proof. An account key alone does not register a public OAuth client.

Save changed settings before signing in or refreshing. The app refuses to start from an unsaved destination. HTTPS is the default. Unencrypted private-server authorization requires the explicit checkbox; credentials then travel without application-layer transport encryption, so use only a deliberately trusted private connection. No scheme downgrade, redirect following or credential forwarding to a different host is performed.

Sign in with browser opens the system's external browser. The app creates secure transaction-specific state and proof material; the verifier remains private and never appears in the authorization URL. Pending browser proof is saved only in the existing encrypted app state so a process restart can receive the original return. Only the exact application callback URI, matching state, current connection binding and unexpired flow can submit a code to the configured token endpoint. Duplicate parameters, old returns and replayed results do not alter the current state. A successful token exchange stores the actual returned bearer credential in existing encrypted app state and retains the original API-key fields.

Each sign-in is bound to the saved authorization settings, model endpoint, API format and selected workspace. A changed destination cannot receive a previously bound access or refresh credential. A fresh sign-in creates a new authorization identity. Private server-search thinking/signature blocks from an earlier authorization identity remain retained locally but are not sent under the new one. Refreshing the same authorization identity retains its eligible server context.

Refresh authorization explicitly submits the saved refresh credential to the configured token endpoint. Model requests also refresh known-expiring credentials before submission, across ordinary turns, reviewed child tasks, captured parent continuations and paused server-search turns. A successful owned refresh resumes that original request once. It preserves eligible same-account server context and the existing expiring voice consent. Changed conversation, routing or workspace context cannot resume the old request; unowned credential changes cannot inherit voice consent. Very short token lifetimes do not create a refresh loop.

Returned refresh credentials rotate atomically with the access token. If a refresh response omits a new refresh credential, the matching previous credential is retained; a fresh sign-in never inherits another account's refresh credential. Before dispatching a rotating refresh, the app records that its outcome is unconfirmed. A successful owned response clears this condition. A confirmed pre-send failure permits another explicit attempt; a sent, cancelled, interrupted or malformed exchange is not replayed. Sign in again if that outcome is unconfirmed. Known-expired credentials without a usable refresh credential are refused before model submission. This never retries an already-submitted model request.

Use existing API-key settings switches that connection back to its retained key. Saved authorization credentials remain encrypted. This local mode switch does not claim to revoke the server's grant. Configuration exports and normal authorization views omit access tokens, refresh tokens, original API keys and proof material. Model requests use the bearer header only for the selected bound connection, across all four supported model formats; metadata and model-list probes use the same authorization function.

Cancel authorization retires only its pending flow and retains existing credentials. Browser flows expire after ten minutes, including time outside the app. Process recovery can restore only an unexpired browser flow from encrypted state, with the same saved connection, workspace and application redirect. It does not reopen the browser or submit anything until the exact matching return arrives. Expired, future-dated, changed or invalid proof is retired and usable authorization settings are shown. The saved proof is retired before exchanging the code. Recovery never replays a code exchange, rotating refresh, model request or microphone session. Signing in must start when the current operation is idle, and leaving the pending authorization flow retires its browser return. Errors remain local to authorization; local work, other connections and retained API-key mode remain available.

The protocol/security design follows [native-app authorization](https://www.rfc-editor.org/rfc/rfc8252.html), [proof-key exchange](https://www.rfc-editor.org/rfc/rfc7636.html), [bearer tokens](https://www.rfc-editor.org/rfc/rfc6750.html) and [current authorization security practice](https://www.rfc-editor.org/rfc/rfc9700.html). Actual local HTTP tests exercise S256 code verification, token exchange, rotation, destination binding and model requests. Installed Android browser return, Keystore persistence and live authorization-server acceptance require device execution. Confidential-client secrets and proof-of-possession token methods are not advertised by this public-client flow.

## Device authorization

Compatible servers may instead expose a device authorization endpoint. Configure that optional endpoint, the token endpoint, registered public client identifier and scopes in Connection authorization. A device-only configuration need not invent a browser authorization endpoint. Existing browser authorization and API-key settings remain available independently.

Choose Sign in with device code to request a new code. The app displays the actual verification address and user code. Verify these on the configured authorization server; Open verification address is an explicit external-browser action. The optional pre-completed verification URL is not used. The private device credential stays in process-owned memory and is never put in the authorization UI, configuration export or saved app state.

Check authorization sends one status request only after the server's minimum interval (five seconds when omitted). A pending response keeps the same code; slow_down increases the interval by five seconds for all later checks. The app never polls unattended or starts a new grant automatically. Denial, expiry, unsupported errors and uncertain transport outcomes retire the grant without replay. The local session also expires after at most ten minutes. Token success uses the same bound bearer adoption, account identity and atomic refresh lifecycle as browser sign-in. Actual source responses and unique request nonces prevent an older phase or poll callback from satisfying a newer exchange.

Returning to the activity in the same process retains an unexpired waiting code without a request. Process restart retires that code and requires an explicit new sign-in; it cannot recover or replay private device credentials. Closing, cancelling, changing the connection/workspace or starting other work retires the waiting flow. A denied optional grant leaves API-key settings and unrelated local work intact. Physical browser/Android/live-server acceptance remains separate from owner HTTP validation.

The device grant follows https://www.rfc-editor.org/rfc/rfc8628.html . It is an optional compatibility method for configured servers; browser authorization with proof-key exchange remains available on capable devices.
